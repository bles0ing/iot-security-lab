# RS485 双板指令扫描系统技术报告

## 一、项目概述

### 1.1 项目背景

本项目目标是构建一个基于 RS485 总线的**双 STM32F103 板指令扫描系统**：一块板（Scanner）依次发送指令字节 `0x01`~`0x08`，另一块板（Receiver）根据指令有效性回复 `ACK` 或 `NAK`，Scanner 收到应答后在 OLED 与串口上打印该指令码及结果。

项目并非简单的"点灯通信"，而是一次**完整的嵌入式调试训练**：从驱动层、中断层到应用层，逐步暴露并解决了多个实际问题，最终形成一套可靠的半双工通信方案。

### 1.2 硬件配置

| 模块 | 具体型号/引脚 | 作用 |
|------|--------------|------|
| MCU | STM32F103C8T6 ×2 | Scanner / Receiver |
| RS485 收发器 | MAX485 / SP3485 ×2 | 电平转换、方向控制 |
| OLED | 0.96 寸 I2C ×2 | 状态显示 |
| 调试串口 | USB 转串口模块 + USART1（PA9/PA10） | Scanner 侧打印调试信息 |
| LED | 正常→PA2，异常→PA3 | 视觉指示 |
| 按键 | 一路 GPIO | 手动触发发送 |

**UART3 引脚映射（Scanner / Receiver 均为此配置）：**

| 信号 | 引脚 | 方向 | 说明 |
|------|------|------|------|
| DI (Data In) | PB10 | MCU → 收发器 | UART3_TX，发送数据 |
| RO (Receive Out) | PB11 | 收发器 → MCU | UART3_RX，接收数据 |
| DE (Driver Enable) | PB9 | MCU → 收发器 | 高电平=发送使能 |
| RE (Receive Enable) | PB8 | MCU → 收发器 | **低电平=接收使能**（注意逻辑相反）|

> **关键说明**：DE 与 RE 分开由 PB9 / PB8 控制，且两者**逻辑电平相反**——发送时需 `DE=高, RE=低`，接收时需 `DE=低, RE=高`。这与常见的"DE/RE 短接由单引脚控制"不同，是本项目硬件设计的一个要点。

### 1.3 接线拓扑

```
Scanner (板A)                     Receiver (板B)              电脑
  PB10 (DI) ──────────────────────── PA9 (RO)                    │
  PB11 (RO) ──────────────────────── PA10 (DI)                  │
  PB9 (DE) ─┐                    ┌─ PC13 (DE)                   │
  PB8 (RE) ─┼─ 控制方向           ┼─ PC13 (RE)                   │
            │                    │                              │
  A (+) ─────────────────────────── A (+)                        │
  B (-) ─────────────────────────── B (-)                        │
  GND ───────────────────────────── GND                          │
                                                                 │
  USART1 (PA9/PA10) ── USB转串口 ───────────────────────────────┘
        ↑
   printf 调试输出
```

## 二、协议设计

### 2.1 指令集

Scanner 依次发送 `0x01`~`0x08` 共 8 个指令字节。Receiver 判定规则：

| 指令码 | 有效性 | Receiver 回复 | LED（Scanner 侧） |
|--------|--------|---------------|-------------------|
| `0x01` | 无效 | `NAK` | PA3（异常） |
| `0x02` | 无效 | `NAK` | PA3（异常） |
| `0x03` | **有效** | **`ACK`** | PA2（正常） |
| `0x04` | 无效 | `NAK` | PA3（异常） |
| `0x05` | 无效 | `NAK` | PA3（异常） |
| `0x06` | **有效** | **`ACK`** | PA2（正常） |
| `0x07` | 无效 | `NAK` | PA3（异常） |
| `0x08` | 无效 | `NAK` | PA3（异常） |

**有效指令码**：`0x03`、`0x06`

**应答格式**：ASCII 字符串 `"ACK"`（0x41 0x43 0x4B）或 `"NAK"`（0x4E 0x41 0x4B），固定 3 字节。

### 2.2 通信时序

```
Scanner                              Receiver
   |                                    |
   |  ---- 0x03 (有效指令) ---->        |
   |                                    | 判断首字节 == 0x03
   |  <--- "ACK" (3字节) ----------     |
   |                                    |
   |  ---- 0x01 (无效指令) ---->        |
   |                                    | 判断首字节 != 0x03/0x06
   |  <--- "NAK" (3字节) ----------     |
   |                                    |
   |  ... 依次扫描 0x01 ~ 0x08 ...     |
```

## 三、调试过程记录（核心章节）

本章按**时间线**还原真实调试过程。每个问题均采用统一的四段式结构：**现象 → 猜想与验证 → 根因分析 → 解决方案**，重点记录"如何确认原因"的工程方法。

### 阶段一：OLED 只刷新一次，系统卡死

#### 现象
系统上电后，OLED 第一次显示正常，此后无论怎么触发，画面不再更新，按键也无响应。

#### 猜想与验证
- **猜想 1**：OLED 驱动本身有问题？
  - *验证*：单独测试 OLED 刷屏函数，正常——排除驱动。
- **猜想 2**：UART 中断卡住了主循环？
  - *验证*：在 `HAL_UARTEx_RxEventCallback` 里加调试打印，发现回调被反复触发，且每次都在执行 OLED 刷新代码。
  - **关键观察**：用示波器（或用逻辑分析仪）观察发现，OLED 刷新耗时约 **2~5ms**，而 RS485 空闲中断在此期间持续到来——**中断服务程序（ISR）里做耗时操作，导致主循环饿死**。

#### 根因分析
`HAL_UARTEx_RxEventCallback` 是中断上下文，在里面调用 `OLED_CLS()`、`OLED_ShowString_F8X16()` 等 I2C 写屏函数（毫秒级），加上 `HAL_Delay(10)`，**阻塞了中断返回**，主循环得不到执行时间。

#### 解决方案
**中断里只置标志，主循环里处理业务**：
- 回调中仅 `Rx_flag = 1;`，并立即重新开启 `HAL_UARTEx_ReceiveToIdle_IT`。
- 主循环 `while(1)` 中轮询 `Rx_flag`，在**非中断上下文**中执行 OLED 刷新、协议判断、应答发送。

> **工程原则**：ISR 应"快进快出"，只做最轻量的事（置标志、清标志、拷贝数据）。

### 阶段二：指令码永远"错一位"

#### 现象
发送 `0x03`（有效指令），Scanner 收到 `ACK` 后 OLED 却显示下一条 `0x04` 的信息；发送 `0x06` 却显示 `0x07`。**打印的总是"下一个尚未发送的字节"。**

#### 猜想与验证
- **猜想 1**：协议判断写错了？
  - *验证*：单独打印 `RS485_RxBuf` 内容，确认收到的确实是 `"ACK"`——协议判断无误。
- **猜想 2**：索引变量出了问题？
  - *验证*：在接收处理中打印 `count` 与 `cnt` 两个变量的值，发现**两者不同步**：
    - 按键发送用 `count`（发送后 `count++`）
    - 接收处理用 `cnt`（接收后 `cnt++`）
  - **关键观察**：当总线上出现一次"额外接收事件"（详见阶段四）时，`cnt` 会比 `count` 多递增一次，从此错位，且**永远无法自行恢复**。

#### 根因分析
两个独立计数器（`count` 与 `cnt`）在**异步中断环境**下无法保持同步。任何一次多余的空闲中断都会让 `cnt` 超前，导致打印索引偏离。

#### 解决方案
**统一使用单一索引变量 `count`**：
- 发送：`arr[count]`，发送后 `count++`
- 接收处理：打印 `arr[count - 1]`（即**刚发送的字节**）
- **彻底删除 `cnt` 变量**，消除失步可能。

---

### 阶段三：互换角色后通信失败——怀疑板级硬件

#### 现象
将两块板互换角色（A 当 Receiver、B 当 Scanner）后，接收方完全收不到数据；且这块板在做 **CAN 回环测试时也失败**（CAN 回环是芯片内部自发自收，不走外部引脚）。

#### 猜想与验证
- **猜想 1**：软件配置问题？
  - *验证*：同一份代码烧录到另一块同型号板 → **CAN 回环通过、UART 接收正常**。排除软件。
- **猜想 2**：该板的 RX 引脚到收发器 RO 没接好？
  - *验证*：CAN 回环不走外部 RX 引脚仍失败 → **不是接线问题，而是板级/芯片级问题**。
- **猜想 3**：芯片在 CAN 实验时受损？
  - *验证*：该板"发送（TX）正常，接收（RX）异常"，且跨 UART/CAN 两个外设复现 → **高度怀疑该板的通信外设域或 IO 受损**（可能源于 CAN 实验时的接线错误/过压）。

#### 根因分析
该板的 **UART RX 通路（及 CAN 外设）存在硬件缺陷**——可能是 IO 口、外设供电域或时钟树在之前的实验中受损，表现为"能发不能收"，且软件层面无法修复。

#### 解决方案
- **角色固定**：让该板专职担任 **Scanner（发送方，TX 正常）**，另一块正常的板担任 **Receiver（接收方）**。
- **长期方案**：更换新板，旧板仅用于不依赖接收外设的实验（GPIO、定时器等）。

### 阶段四（关键转折）：复位接收端，发送端"鬼影触发"

#### 现象
**没有按任何按键**，仅按下 Receiver 的复位键，Scanner 的 OLED 竟突然显示 `01`（`arr[0]`）并执行了一次接收处理——仿佛收到了一条指令。

#### 猜想与验证
- **猜想 1**：代码逻辑 bug，误触发？
  - *验证*：检查主循环，确认只有 `Rx_flag=1` 时才进入接收处理。说明 **`Rx_flag` 确实被置 1 了**，即回调确实被调用了。
- **猜想 2**：复位瞬间总线产生了噪声？
  - *验证*：在回调中**打印原始接收数据与长度**（`RS485_RxBuf` 前几字节 + `rx_len`），发现：
    - 正常 `ACK`：`41 43 4B`，`rx_len=3`
    - **复位瞬间**：`00 00 00 ...` 或 `FF FF ...`，`rx_len` 为随机值
  - **关键观察**：这些乱码**前 3 字节既不是 `"ACK"` 也不是 `"NAK"`**，但旧代码并未校验内容，直接执行了显示与计数逻辑。

#### 根因分析（因果链串联）
```
复位 Receiver
    ↓
RS485 总线电平波动（噪声）
    ↓
Scanner 的 UART 误判为起始位 → 触发空闲中断
    ↓
回调置 Rx_flag=1 → 主循环执行接收处理
    ↓
旧代码：显示 arr[cnt]、cnt++（无论数据是否合法）
    ↓
【这就是阶段二"错一位"的真正源头：
 噪声伪造了一次"假接收"，让 cnt 提前递增】
```

**换言之**：阶段四发现的"噪声伪造接收"正是阶段二"索引错位"的根本原因。之前用 `cnt` 只是放大了这个问题。

#### 解决方案
**数据合法性过滤（协议层防御）**：在接收处理中，仅当**前 3 字节严格匹配 `"ACK"` 或 `"NAK"`** 时才执行后续逻辑，否则**直接丢弃，不改变任何状态变量**：

```c
// 伪代码逻辑（非代码文件，仅说明思路）
if (rx_len >= 3 &&
    (memcmp(RS485_RxBuf, "ACK", 3) == 0 ||
     memcmp(RS485_RxBuf, "NAK", 3) == 0)) {
    // 合法应答 → 显示、打印 arr[count-1]
} else {
    // 噪声/残帧 → 忽略，count/cnt 均不变
}
```

**效果**：复位噪声被挡在业务逻辑之外，计数状态永不失步。

### 问题因果链总览

```
阶段一：中断里做耗时操作 → OLED 卡死
            ↓ （解决后暴露下一层问题）
阶段二：count 与 cnt 异步失步 → 指令码错一位
            ↓ （追查根源）
阶段三：硬件受损 → 接收通路不稳定（独立的板级问题）
            ↓
阶段四：噪声伪造接收事件 → cnt 提前递增 ← 这才是阶段二的真因

```

**核心结论**：阶段四发现的"上电/复位噪声伪造接收"是贯穿多个问题的**根因**。通过协议层过滤（`memcmp`）+ 单一索引变量（`count`），系统最终实现了可靠的指令扫描。

## 四、软件架构

### 4.1 分层设计

```
┌─────────────────────────────────────────┐
│  应用层 (app_rs485)                     │
│  - RS485_Scan(): 按键发送 + 接收处理   │
│  - 协议判断 (ACK/NAK)                  │
│  - 状态显示 (OLED / LED / printf)      │
├─────────────────────────────────────────┤
│  驱动层 (HAL + 外设初始化)             │
│  - UART3: HAL_UARTEx_ReceiveToIdle_IT  │
│  - GPIO: DE/PB9, RE/PB8 方向控制       │
│  - OLED (I2C), LED (PA2/PA3), 按键    │
├─────────────────────────────────────────┤
│  中断层 (ISR)                          │
│  - HAL_UARTEx_RxEventCallback          │
│  - 仅置 Rx_flag，快进快出              │
└─────────────────────────────────────────┘
```

### 4.2 关键设计原则

1. **ISR 最小化**：回调中只置标志，业务处理在主循环。
2. **单一数据源**：索引变量 `count` 统一管理，避免多计数器失步。
3. **协议过滤**：所有接收数据先校验合法性，非法数据丢弃。
4. **方向切换规范**：发送前 `DE=高, RE=低`；发送后（TC 等待完成）`DE=低, RE=高`。

## 六、调试方法论总结

1. **ISR 快进快出**——耗时操作移出中断。
2. **单一索引变量**——异步环境下多计数器必失步。
3. **协议合法性校验**——`memcmp` 过滤是最简单有效的噪声防御。
4. **现象→猜想→验证→结论**——每一步都用可观测数据（printf、OLED 显示、逻辑分析仪）支撑。
5. **换板验证**——区分"软件问题"与"硬件问题"的最快手段。
6. **因果链追溯**——表象问题的根因往往在更底层（如阶段四 → 阶段二）。
